# Multi-Database Architecture Plan

## Current State

Single `data.db` with all 15 tables, single `db/gen/` (sqlc), single `*sql.DB` + `*gen.Queries`.

```
[One SQLite file]
  ├── master_contracts (read-heavy, daily refresh, 100k+ rows)
  ├── watchlist_items + watchlists (read by broker stream)
  ├── brokers (write: connect, update tokens)
  ├── orders + positions + strategy_positions (write-heavy per trade)
  ├── strategies + strategy_joiners + strategy_info + strategy_types
  └── system_settings + broker_columns + broker_list (rare writes)
```

## Proposed Split

Two SQLite files → same pattern works for PostgreSQL (two databases on same server):

```
data-market.db                          data-trading.db
├── master_contracts                    ├── brokers
├── watchlist_items                     ├── orders
├── watchlists                          ├── positions
├── system_settings                     ├── strategy_positions
                                        ├── strategies
                                        ├── strategy_joiners
                                        ├── strategy_info
                                        ├── strategy_types
                                        ├── broker_columns
                                        ├── broker_list
```

**Rationale**: `master_contracts` is a 100k+ row bulk table refreshed daily — keeping it isolated means:
- DDL migrations never block trading DB
- Full-table `DELETE`/`INSERT` during contract download only locks the market DB
- Broker stream reads (`LoadTokenSymbolMap`, `LoadWatchlistSymbols`) don't contend with order writes
- DB file size stays manageable (<50MB each vs potentially 200MB+ combined)

**`db/trading/schema.sql`** — trading DB tables:

```sql
CREATE TABLE IF NOT EXISTS strategies (...);
CREATE TABLE IF NOT EXISTS strategy_joiners (...);
CREATE TABLE IF NOT EXISTS strategy_info (...);
CREATE TABLE IF NOT EXISTS strategy_types (...);
CREATE TABLE IF NOT EXISTS broker_columns (...);
CREATE TABLE IF NOT EXISTS broker_list (...);
```

**`sqlc.yaml`** — two gen packages:
```yaml
version: "2"
sql:
  - engine: sqlite
    schema: db/market/schema.sql
    queries: db/market/query.sql
    gen:
      go:
        package: "marketdb"
        out: "db/market/gen"
  - engine: sqlite
    schema: db/trading/schema.sql
    queries: db/trading/query.sql
    gen:
      go:
        package: "tradingdb"
        out: "db/trading/gen"
```

Generated code paths:
- `db/market/gen/` → package `marketdb`
- `db/trading/gen/` → package `tradingdb`

### Step 2: Dual DB initialization in `internal/db/db.go`

```go
type Databases struct {
    Market  *sql.DB
    Trading *sql.DB
    MarketQ  *marketdb.Queries
    TradingQ *tradingdb.Queries
}

func New(cfg *config.Config) (*Databases, error) {
    marketDB, err := sql.Open("sqlite", cfg.MarketDBPath)   // "data-market.db"
    tradingDB, err := sql.Open("sqlite", cfg.TradingDBPath) // "data-trading.db"
    
    // PRAGMAs on both
    maxConns := runtime.GOMAXPROCS(0) * 2
    for _, db := range []*sql.DB{marketDB, tradingDB} {
        db.SetMaxOpenConns(maxConns)
        db.SetMaxIdleConns(maxConns)     // idle = max — keeps connections warm, avoids
        db.SetConnMaxLifetime(30 * time.Minute) // re-opening socket file handles per request
        db.Exec("PRAGMA journal_mode=WAL")
        db.Exec("PRAGMA busy_timeout=5000")
        db.Exec("PRAGMA cache_size=-8000")
    }
    
    return &Databases{
        Market:    marketDB,
        Trading:   tradingDB,
        MarketQ:   marketdb.New(marketDB),
        TradingQ:  tradingdb.New(tradingDB),
    }, nil
}
```

### Step 7: PostgreSQL migration path

The module structure stays the same. Only the driver changes:

```go
// SQLite today
import _ "modernc.org/sqlite"
marketDB, _ := sql.Open("sqlite", "data-market.db")

// PostgreSQL later
import _ "github.com/jackc/pgx/v5/stdlib"
marketDB, _ := sql.Open("pgx", "postgres://user:pass@host:5432/bhavyaai_market")
tradingDB, _ := sql.Open("pgx", "postgres://user:pass@host:5432/bhavyaai_trading")
```

Two databases on the same Postgres server = two connection strings with different `dbname` params.
No sqlc changes needed — sqlc generates Go code using `database/sql` interfaces.

**⚠️ `sql.Result.LastInsertId()` does NOT work on PostgreSQL.**
SQLite returns the last auto-increment ID from `res.LastInsertId()`. PostgreSQL does not support this — it always returns 0. Both engines support `RETURNING id`:

```go
// SQLite-only (BROKEN on Postgres):
res, _ := db.Exec(`INSERT INTO orders (...) VALUES (...)`)
id, _ := res.LastInsertId()

// Portable (works on BOTH SQLite and Postgres):
var id int64
db.QueryRowContext(ctx, `INSERT INTO orders (...) VALUES (...) RETURNING id`).Scan(&id)
```

**Fix**: Audit all insert queries now. Any that currently rely on `LastInsertId()` must switch to `RETURNING id` + `QueryRowContext().Scan()`. sqlc-generated `:one` queries already use `RETURNING` — the risk is in raw SQL inserts outside sqlc (e.g., `connect_broker.go` updates, `db.go` migrations).

**⚠️ PostgreSQL dialect differences to handle**:
| SQLite | PostgreSQL |
|--------|------------|
| `datetime('now')` | `NOW()` or `CURRENT_TIMESTAMP` |
| `INSERT ... ON CONFLICT` | `INSERT ... ON CONFLICT DO UPDATE` |
| `RETURNING` | `RETURNING` ✅ (both support) |
| `CREATE TABLE IF NOT EXISTS` | same ✅ |
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `SERIAL PRIMARY KEY` or `BIGSERIAL` |
| `?` placeholders | `$1`, `$2` numbered placeholders (sqlc handles this per-engine) |
| `TEXT NOT NULL DEFAULT ''` | same ✅ |
| `REAL` | `DOUBLE PRECISION` or `NUMERIC` |

These need to be managed in separate schema files per engine, or use a migration tool (golang-migrate).

## Trade-offs

### ✅ Benefits
- **Write throughput**: Live data writes (ticks stored by broker stream) don't block order placement
- **DDL isolation**: Contract refresh (`DELETE + INSERT master_contracts`) never locks trading queries
- **Backup granularity**: Can backup trading DB more frequently (critical) than market DB (static daily copy)
- **PostgreSQL compatible**: Same split works — two databases on one Postgres server
- **File size**: Each DB stays under 50MB vs potential 200MB+ combined

### ⚠️ Risks
- **No cross-DB SQL JOINs**: sqlc generates two isolated packages (`marketdb`, `tradingdb`). A SQL query cannot JOIN across them. Any cross-DB data assembly must happen **in Go code** (application-level join):
  ```go
  // Example: render a watchlist item with broker metadata
  // Step 1: get watchlist items from Market DB
  items, _ := s.MarketQ.ListWatchlistItems(ctx, watchlistID)
  
  // Step 2: collect broker IDs referenced by items
  brokerIDs := extractBrokerIDs(items)
  
  // Step 3: get broker metadata from Trading DB
  brokers, _ := s.TradingQ.ListBrokersByIDs(ctx, brokerIDs)
  
  // Step 4: merge in Go
  response := mergeItemsWithBrokers(items, brokers)
  ```
  This is explicit and testable but adds a round-trip. For watchlist rendering this is fine (a few items). For batch operations across 1000+ items, you'd want a different strategy (bulk fetch + local map lookup).

- **No cross-DB transactions**: An operation needing atomic writes across both DBs is impossible. Currently no handler does this, but future features (e.g., "atomically check contract AND place order") would break. Mitigation: keep a `data-global.db` for truly shared lookup tables if needed later.

- **Connection overhead**: Two connections instead of one (negligible for SQLite)
- **Deployment complexity**: Two DB files to back up, migrate, monitor
- **sqlc regeneration**: Two `sqlc generate` commands or a multi-package config
- **Code diff**: Every handler must choose the correct `Q` instance

### ❌ When to NOT split
If a future feature requires a transaction spanning both databases (e.g., "atomically check broker token AND read master contract AND place order"), the split breaks. In that case, keep a single DB. The split is a performance optimization, not a correctness requirement.

## Implementation Order

1. **Create `db/market/` and `db/trading/` directories** with split `schema.sql` and `query.sql` files
2. **Update `sqlc.yaml`** for two gen packages, run `sqlc generate`
3. **Update `internal/db/db.go`** → `New()` returns `*Databases` with both `*sql.DB` and both `*gen.Queries`
4. **Update `internal/server/`** → `Server` struct holds both Q instances, each handler uses correct one
5. **Update `blueprints/`** → `App` struct holds both Q instances, update raw SQL to use correct `*sql.DB`
6. **Update `main.go`** → pass both DBs through the dependency chain
7. **Update `internal/setup/`** → `SeedFromFile` and `DownloadMasterContract` use correct Q instance
8. **Run `go build ./...`** — fix all compilation errors
9. **Run `sqlc generate`** as part of build pipeline
